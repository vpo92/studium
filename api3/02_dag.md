# Dossier d’Architecture Générale (DAG) : Studium\n\n## Informations générales\n- **Projet :** Studium\n- **Produit / Domaine :** Base de données prosopographique / Médiévistique\n- **Version :** 1.0.0\n- **Date :** 2023-10-27\n- **Auteur(s) :** Agent Architecte d\'Entreprise\n- **Statut :** Draft\n\n---\n\n# 1. Contexte et objectifs\n\n## 1.1 Contexte\nDécrire le contexte métier et/ou réglementaire :\n- Le LAMOP (Laboratoire de Médiévistique Occidentale de Paris) de l\'Université Paris 1 dispose d\'une base de données prosopographique sous forme de fichier TXT balisé.\n- Ce fichier est difficilement interrogeable et exploitable, limitant l\'accès et l\'utilisation des informations qu\'il contient.\n- Il n\'existe pas d\'application dédiée, la saisie et la consultation se font manuellement, avec des risques de corruption des données et une collaboration difficile.\n\n## 1.2 Objectifs\n- **Objectif métier :** Rendre la base de données prosopographique facilement interrogeable, notamment en langage naturel via une intelligence artificielle, pour faciliter l\'accès et l\'exploitation des informations.\n- **Objectif IT :** Développer une solution agnostique au LLM, open-source, permettant la consultation (index alphabétique, recherche texte intégral, avancée, langage naturel), la gestion (création, modification, archivage) et l\'administration (gestion des comptes, sauvegarde, téléchargement) des fiches.\n- **Contraintes :**\n    - Budget limité (environnement universitaire).\n    - Toutes les briques et technologies doivent être open-source.\n    - L\'utilisation d\'un LLM externe est tolérée dans un premier temps, mais la solution doit être agnostique au LLM.\n    - Délai de 6 mois.\n    - Authentification via OAuth2.\n    - Infrastructure 100% conteneurisée et \"infra as code\" basée sur docker-compose.\n    - Technologies : Front Vue.js 3 / Tailwind, Back Python (FastAPI).\n\n---\n\n# 2. Gère le contenu des prosopographies (création, modification, archivage).\n- **Administrateur :** Gère le système (comptes utilisateurs, sauvegardes, téléchargement de la base).\n\n## 2.3 Processus métier\n**Workflow global :**\n1.  **Visiteur :** Accède à l\'application → Choisit un mode de recherche (index, texte intégral, avancé, langage naturel) → Consulte les fiches.\n2.  **Rédacteur :** Accède à l\'application → Crée/Modifie/Archive une fiche → Soumet la fiche.\n3.  **Administrateur :** Accède à l\'application → Gère les comptes / Effectue une sauvegarde / Télécharge la base de données.\n\n### Déclencheur\n- Accès à l\'application par un utilisateur.\n- Besoin de créer/modifier/archiver une fiche.\n- Nécessité de gérer les utilisateurs ou de sauvegarder les données.\n\n### Résultat\n- Consultation réussie des fiches.\n- Fiche prosopographique créée/modifiée/archivée.\n- Comptes utilisateurs gérés, base de données sauvegardée/téléchargée.\n\n---\n\n# 3. Architecture Fonctionnelle\n\n## 3.1 Vue d’ensemble\nLe système Studium offrira une interface web permettant aux utilisateurs (Visiteurs, Rédacteurs, Administrateurs) d\'interagir avec une base de données prosopographique. Il intégrera des fonctionnalités de recherche avancée, de gestion de contenu et d\'administration, avec une capacité d\'interrogation en langage naturel via une IA.\n\n## 3.2 Découpage fonctionnel\n-   **Module de Consultation**\n    -   Description : Permet aux visiteurs de rechercher et visualiser les fiches prosopographiques.\n    -   Fonctions :\n        -   Consultation via index alphabétique\n        -   Recherche en texte intégral\n        -   Recherche avancée par critères\n        -   Recherche en langage naturel (intégration IA)\n-   **Module de Gestion des Fiches**\n    -   Description : Permet aux rédacteurs de gérer le cycle de vie des fiches prosopographiques.\n    -   Fonctions :\n        -   Création de fiches\n        -   Modification de fiches\n        -   Archivage de fiches\n-   **Module d\'Administration**\n    -   Description : Permet aux administrateurs de gérer les utilisateurs et la base de données.\n    -   Fonctions :\n        -   Gestion des comptes utilisateurs (création, modification, suppression)\n        -   Sauvegarde de la base de données\n        -   Téléchargement de la base de données\n-   **Module d\'Authentification et d\'Autorisation**\n    -   Description : Gère l\'accès sécurisé au système et les droits des utilisateurs.\n    -   Fonctions :\n        -   Authentification OAuth2\n        -   Gestion des rôles et permissions\n\n## 3.3 Flux et interactions\n\n> *la liste des flux. Architecture Applicative\n\n## 4.1 Cartographie des composants\n-   **Frontend**\n    -   Type : SPA (Single Page Application)\n    -   Description : Interface utilisateur développée en Vue.js 3 (via CDN) et HTML5/Tailwind CSS, offrant les fonctionnalités de consultation, gestion et administration.\n-   **API Gateway**\n    -   Rôle : Non explicitement défini comme un composant séparé. Les fonctionnalités de routage et de sécurité (OAuth2) seront gérées par le backend FastAPI.\n-   **Backend**\n    -   Type : Monolithe (FastAPI)\n    -   Description : Application Python FastAPI exposant les API REST pour la gestion des fiches, l\'administration et l\'intégration avec le service LLM. Il intègre également le module d\'authentification OAuth2 et gère l\'interaction avec **ChromaDB (en mémoire)** pour l\'indexation et la recherche vectorielle, ainsi que la lecture/écriture du fichier TXT/JSON source pour la persistance des données.\n-   **Services externes**\n    -   **Service LLM Externe :** Fournit la capacité d\'interrogation en langage naturel. La solution doit être agnostique au LLM pour permettre un remplacement ultérieur.\n\n## 4.2 Interfaces / APIs\n| API | Type | Description |\n|----|-----|------------|\n| `/api/auth/login` | REST (POST) | Authentification des utilisateurs (OAuth2 Password Bearer). |\n| `/api/fiches` | REST (GET, POST, PUT, DELETE) | Gestion des fiches prosopographiques (CRUD). |\n| `/api/search` | REST (GET) | Recherche en texte intégral et avancée. |\n| `/api/llm-query` | REST (POST) | Interface pour les requêtes en langage naturel vers le service LLM externe. |\n| `/api/admin/users` | REST (GET, POST, PUT, DELETE) | Gestion des comptes utilisateurs. |\n| `/api/admin/backup` | REST (POST) | Déclenchement de la sauvegarde de la base de données. |\n| `/api/admin/download` | REST (GET) | Téléchargement de la base de données. |\n\n---\n\n# 5. Architecture des Données (Data Architecture)\n\n## 5.1 Principes\n- **Type de base de données :** Vector Store en mémoire (ChromaDB) pour l\'interrogation et la recherche, avec le fichier TXT/JSON initial comme source de vérité pour la persistance des données.\n- **Structure des documents :** Chaque enregistrement est un document JSON avec `_id` (UUID v4), `created_at` et `updated_at`.\n- **Gouvernance :** Les données sont classifiées comme \"Publiques\" selon le dossier de cadrage.\n\n## 5.2 Modèle de données\n\n| Entité | Description | Sensibilité | Source |\n|-------|------------|------------|--------|\n| Fiche Prosopographique | Contient les informations détaillées sur une personne médiévale. | Public | Fichier TXT/JSON initial, puis saisie Rédacteur via l\'application |\n| Utilisateur | Informations sur les Visiteurs, Rédacteurs, Administrateurs. | Interne | Saisie Administrateur |\n\n> *[diagramme entité-relation sans les attributs]*\n```mermaid\nerDiagram\n    \"Fiche Prosopographique\" {\n        string _id PK\n        string created_at\n        string updated_at\n        string contenu\n        string statut\n    }\n    \"Utilisateur\" {\n        string _id PK\n        string created_at\n        string updated_at\n        string nom\n        string prenom\n        string email\n        string role\n    }\n    \"Utilisateur\" ||--o{ \"Fiche Prosopographique\" : \"gère\"\n```\n\n## 5.3 Cycle de vie des données\n- **Création :** Les fiches sont créées par les Rédacteurs via le Module de Gestion des Fiches. Ces modifications sont appliquées à ChromaDB en mémoire et doivent être persistées dans le fichier TXT/JSON source. Les comptes utilisateurs sont créés par les Administrateurs et stockés dans le fichier TXT/JSON.\n- **Stockage :** Les données sont chargées dans ChromaDB en mémoire au démarrage de l\'application. La source de vérité persistante est le fichier TXT/JSON (`database.json` ou équivalent).\n- **Archivage :** Les fiches peuvent être marquées comme \"archivées\" par les Rédacteurs. Cette modification est appliquée à ChromaDB en mémoire et doit être persistée dans le fichier TXT/JSON source.\n- **Suppression :** Les fiches ou comptes utilisateurs peuvent être supprimés par les Administrateurs. Cette modification est appliquée à ChromaDB en mémoire et doit être persistée dans le fichier TXT/JSON source.\n\n## 5.4 RGPD / Sécurité des données\n- **Classification :** Données publiques, aucune contrainte réglementaire spécifique identifiée (hors RGPD général).\n- **Durée de conservation :** Non spécifiée, à définir avec le métier.\n- **Accès :** Contrôlé par le Module d\'Authentification et d\'Autorisation (OAuth2, RBAC).\n\n---\n\n# 6. Architecture Technique / Infrastructure\n\n## 6.1 Environnements\n- **DEV :** Environnement de développement local pour les développeurs.\n- **TEST :** Environnement d\'intégration et de tests (QA, UAT).\n- **PROD :** Environnement de production pour les utilisateurs finaux.\n\n## 6.2 Hébergement\n- **Type :** Conteneurisé (Docker).\n- **Contraintes :** L\'infrastructure est 100% conteneurisée et \"infra as code\" basée sur docker-compose.\n- **Provider :** Non spécifié, mais la solution doit être portable grâce à Docker.\n\n## 6.3 Sécurité\n- **Chiffrement :** TLS pour les communications HTTP/S.\n- **Authentification :** OAuth2 (Password Bearer) via JWT (JSON Web Tokens) pour l\'accès aux API.\n- **Gestion des accès :** RBAC (Role-Based Access Control) basé sur les rôles définis (Visiteur, Rédacteur, Administrateur).\n- **Secrets :** Les secrets (JWT_SECRET) doivent être gérés via variables d\'environnement et non hardcodés.\n\n---\n\n# 7. Non-Fonctionnel (NFR)\n\n## 7.1 Performance\n- **Nombre d\'utilisateurs cible :** 10 à 50 utilisateurs.\n- **Pic d\'utilisation :** 10 utilisateurs simultanés.\n- **Temps de réponse :** Les requêtes API devraient avoir un temps de réponse inférieur à 500ms pour 90% des cas (à affiner).\n\n## 7.2 Disponibilité\n- **% disponibilité :** Non spécifié, mais une disponibilité standard pour une application universitaire est attendue (ex: 99%).\n- **Plan de continuité :** Sauvegarde régulière de la base de données par les administrateurs.\n\n## 7.3 Scalabilité\n- **Capacité :** La solution doit être capable de gérer 10 à 50 utilisateurs avec des pics de 10 utilisateurs simultanés. L\'architecture conteneurisée permet une mise à l\'échelle horizontale si nécessaire, bien que TinyDB puisse devenir un goulot d\'étranglement à très grande échelle.\n\n## 7.4 Sécurité\n- **Contrôles :** Authentification OAuth2, autorisation basée sur les rôles, validation des entrées (Pydantic), gestion des erreurs standardisée.\n- **Normes :** Respect des bonnes pratiques de sécurité pour les applications web.\n\n---\n\n# 8. Transverse\n\n-   **Sécurité :** Intégrée à tous les niveaux (authentification, autorisation, validation des données, gestion des secrets).\n-   **Supervision :** Mise en place de logs structurés pour faciliter le monitoring.\n-   **Logging / Monitoring :** Logs au format JSON, centralisation à prévoir si l\'environnement le permet.\n-   **CI/CD :** Pipeline d\'intégration et de déploiement continu à définir pour automatiser les builds et déploiements Docker.\n-   **Gestion documentaire :** Ce DAG fait partie de la documentation du projet.\n-   **Support / Run :** Processus de support et de maintenance à définir.\n\n---\n\n# 9. Risques et contraintes\n\n## 9.1 Risques\n- **Dépendance LLM externe :** Risque lié à la disponibilité, la performance et le coût du service LLM externe. Mitigation : Solution agnostique au LLM pour faciliter un changement.\n- **Corruption des données :** Bien que le système améliore la situation actuelle, le stockage sur fichier JSON peut présenter des risques en cas de manipulation directe ou de crash système. Mitigation : Sauvegardes régulières.\n- **Performance de ChromaDB (en mémoire) et du fichier JSON :** La gestion des données en mémoire avec ChromaDB et la persistance via un fichier JSON pourraient devenir un goulot d\'étranglement si la volumétrie des données ou le nombre d\'utilisateurs simultanés augmente significativement au-delà des prévisions. Le rechargement complet de ChromaDB au démarrage peut également impacter le temps de disponibilité. Mitigation : Surveillance des performances, optimisation des opérations de lecture/écriture du fichier JSON, et prévoir une évolution vers une solution de persistance plus robuste (ex: ChromaDB persistant sur disque, ou une base de données NoSQL dédiée) si nécessaire.\n\n## 9.2 Contraintes\n- **Technique :**\n    - Toutes les briques et technologies doivent être open-source.\n    - Solution agnostique au LLM.\n    - Infrastructure 100% conteneurisée (Docker) et \"infra as code\" (docker-compose).\n    - Technologies : Front Vue.js 3 / Tailwind, Back Python (FastAPI).\n- **Organisationnelle :**\n    - Budget limité (environnement universitaire).\n    - Délai de 6 mois.\n- **Réglementaire :**\n    - Authentification OAuth2.\n    - Respect des principes RGPD (classification \"Public\" des données).\n\n---\n\n# 10.
